# API overview

`@ferriki/core` provides a tested, HTML-focused subset of Shiki's direct
highlighting API for Node.js. This page is the map; the complete reference,
with every type and error code, is
[docs/ferriki-api.md](https://github.com/sebastian-software/ferriki/blob/main/docs/ferriki-api.md).

## One-shot functions

Each one uses the shared singleton and returns a Promise; pass a highlighter as
the first argument and it returns synchronously.

| Function                             | Returns                                              |
| ------------------------------------ | ---------------------------------------------------- |
| `codeToHtml(code, options)`          | Escaped HTML with Shiki's line and token structure   |
| `codeToHtmlWithCss(code, options)`   | `{ html, css }` with nested classes and a stylesheet |
| `getLastGrammarState(code, options)` | A serializable state to continue highlighting later  |

## Highlighters

| Factory                              | Notes                                       |
| ------------------------------------ | ------------------------------------------- |
| `createHighlighter(options)`         | Resolves loaders and promises, then returns |
| `createHighlighterCoreSync(options)` | Accepts already resolved registrations only |
| `getSingletonHighlighter(options)`   | The instance the one-shot functions use     |

A highlighter carries the methods above plus `loadLanguage`, `loadTheme` (and
their `Sync` forms), `getLoadedLanguages`, `getLoadedThemes`,
`resolveLangAlias` and `dispose`.

## Highlighter options

Factory options include `langs`, `themes`, `langAlias`, `transformers`,
`assets` and `regexPrefilter`. Keep `regexPrefilter: true` (the default) for
reused highlighters in a CMS or site build. For a short-lived process,
`regexPrefilter: false` avoids building the regex prefilter. Matching and
colors stay the same. This is a creation-time option, including the
singleton's first creation; it is not a `HighlightOptions` field.

The [benchmarks](/evidence/benchmarks#first-use-and-the-regex-prefilter) separate
first use from repeated rendering. Top-level shorthand functions reuse the
singleton and do not create a fresh highlighter for each code block.

## Highlight options

The common ones: `lang`, `theme` or `themes`, `defaultColor`,
`cssVariablePrefix`, `styleMode`, `mergeWhitespaces`, `mergeSameStyleTokens`,
`tabindex`, `rootStyle`, `structure`, `meta`, `grammarState` and
`includeExplanation`. `tokenizeTimeLimit` (500 ms per line by default) and
`tokenizeMaxLineLength` bound the work one line may take.

## Errors

Every user-facing failure is a `ShikiError` with a stable `code`
(`ERR_USAGE`, `ERR_UNSUPPORTED`, `ERR_NATIVE_LOAD`, `ERR_ASSET`,
`ERR_RESOURCE_LIMIT`, `ERR_INTERNAL`). Failures inside the native engine are
its subclass `FerrikiError`, so existing `instanceof ShikiError` checks keep
working.

For nested scopes, unchanged theme files, and CSS-only theme switching, see
[Class-based output](/guide/class-highlighting).

## Assets and asynchronous loading

The package ships language and theme catalog metadata, not the grammar and
theme payloads. `createHighlighter`, `loadLanguage`, `loadTheme`, and one-shot
calls download missing payloads from the release-pinned asset host, verify
their SHA-256 digests, and cache them. Calls on a loaded highlighter are
synchronous. Configure `assets: { remote: false }` or
`FERRIKI_ASSETS_REMOTE=0` to use a populated cache without network access;
`assets.baseUrl` and `FERRIKI_ASSETS_BASE_URL` select a mirror.

## Build-time macros

`code()` from `@ferriki/core/macro` and `<Code />` from
`@ferriki/core/react/macro` are markers that `@ferriki/vite` replaces with
highlighted HTML and CSS during a Vite 8 build. [Build-time macros](/guide/build-time-macros)
covers the setup, the macro forms and their rules.
