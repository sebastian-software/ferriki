# Getting started

Ferriki highlights code with the TextMate grammars and themes from Shiki's
catalog, on a native Rust engine. From Node.js it keeps Shiki's rendered HTML
API; in a Vite 8 build, macros prepare code examples at build time
([Build-time macros](/guide/build-time-macros)); from Rust it is a regular crate
([Start with Rust](/rust/getting-started)).

<HighlightingFlows />

## Requirements

- Node.js 22.13.0 or newer. The package is ESM-only: use `import`, not `require()`.
- A supported platform: Linux x64 and arm64 (glibc or musl), macOS on Apple
  Silicon, or Windows x64 and arm64. See [Compatibility](/evidence/compatibility).

## Install

```sh
npm install @ferriki/core
```

The native addon comes from a platform package (`@ferriki/<platform>`) that npm
installs as an optional dependency. Keep optional dependencies enabled in your
deployment.

Grammar and theme payloads are not bundled. The asynchronous APIs download
them from `assets.ferriki.dev` the first time they are loaded, verify each
payload against the release's SHA-256 digest, and cache it in
`node_modules/.cache/ferriki`. To use a mirror, set `FERRIKI_ASSETS_BASE_URL`.
For offline builds, prepopulate the cache or set `FERRIKI_ASSETS_REMOTE=0` and
use cached payloads only. Downloads happen during `createHighlighter`,
`loadLanguage`, `loadTheme`, and one-shot calls; rendering on a loaded
highlighter stays synchronous.

## Highlight once

```js ferriki-check=one-shot
import { codeToHtml } from "@ferriki/core";

const html = await codeToHtml("const answer = 42;", {
  lang: "javascript",
  theme: "github-dark",
});
```

The one-shot functions share a singleton highlighter and return a Promise.
They load the language and theme on first use.
Later calls reuse that singleton, including its loaded languages and themes.

## Reuse a highlighter

For a site build or a server, create one highlighter with the languages and
themes you need. Rendering with loaded languages and themes is synchronous;
you can still load additional ones through the asynchronous methods.
In a CMS, keep it for the worker's lifetime rather than recreating it for
each code block. The [benchmarks](/evidence/benchmarks) measure this repeated use.

```js ferriki-check=reusable
import { createHighlighter } from "@ferriki/core";

const source = "const answer: number = 42;";
const highlighter = await createHighlighter({
  langs: ["typescript", "rust", "css"],
  themes: ["github-light", "github-dark"],
});

let html;
try {
  html = highlighter.codeToHtml(source, { lang: "typescript", theme: "github-light" });
} finally {
  highlighter.dispose();
}
```

A highlighter belongs to one thread: create one per worker for parallel builds.
Dispose it when the build or server no longer needs it.

Keep the default regex prefilter for repeated work. For a short-lived process,
set `regexPrefilter: false` when creating the highlighter to avoid prefilter
construction. This can reduce first-use work; it does not promise a shorter
render for every snippet. See [factory options](/guide/api#highlighter-options)
and the [measured tradeoff](/evidence/benchmarks#first-use-and-the-regex-prefilter).

## HTML with CSS

For reusable CSS classes and the matching theme stylesheet, use
`codeToHtmlWithCss()` or set `styleMode: "classes"` on `codeToHtml()`.

The [API overview](/guide/api) lists every function and option.
