# Migrating from Shiki

Ferriki follows the direct API shape of Shiki **v4.4.3** for a tested subset
and runs it on a native engine. For the highlighting calls, moving over is
usually an import:

```diff
- import { createHighlighter } from "shiki";
+ import { createHighlighter } from "@ferriki/core";

  const highlighter = await createHighlighter({
    langs: ["typescript"],
    themes: ["nord"],
  });

  const html = highlighter.codeToHtml(source, { lang: "typescript", theme: "nord" });
```

## What stays

| Shiki surface                              | In Ferriki                                                                     |
| ------------------------------------------ | ------------------------------------------------------------------------------ |
| `codeToHtml`, `codeToHast`, `codeToTokens` | Supported call shapes; compare output through the notes below                  |
| Reusable highlighters and the singleton    | Same factories; dispose long-lived instances explicitly                        |
| Standard languages, themes and aliases     | `bundledLanguages`, `bundledThemes`, `bundledLanguagesAlias`                   |
| Custom TextMate grammars and themes        | JSON-shaped registrations validated before they reach the engine               |
| `themes` map and `defaultColor: false`     | Supported for light and dark output                                            |
| `transformers` and decorations             | Supported in the JavaScript facade; callbacks stay outside the native boundary |
| `codeToHast` plus `hastToHtml`             | Supported; sanitize at your application boundary                               |
| CSS class output                           | Ferriki extension: `styleMode: 'classes'` or `codeToHtmlWithCss()`             |

## What changes

| Shiki surface                                                    | In Ferriki           | What to do                                                                                                                           |
| ---------------------------------------------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `engine`, `createOnigurumaEngine`, `createJavaScriptRegexEngine` | Removed              | Delete the engine option; Ferriki has one native engine                                                                              |
| `loadWasm`, `wasmBinary`                                         | Removed              | Install the platform package instead                                                                                                 |
| Standard grammar and theme payloads                              | Downloaded on demand | Async factory, load and one-shot calls fetch and verify missing release assets; configure the asset cache or mirror for offline use. |
| Browser runtime                                                  | Not supported        | Highlight in Node.js at build or render time                                                                                         |
| `lang: "ansi"` with escape sequences                             | Rejected             | Strip or parse terminal output first                                                                                                 |
| `rehype`, `markdown-it` and other adapters                       | Not part of Ferriki  | Keep the adapter in your Markdown layer, on top of `codeToHtml` or `codeToHast`                                                      |

"Shiki-compatible" means a tested subset: the baseline and the exclusions are
checked by machine against a pinned mirror of Shiki's own test suite (see
[Compatibility](/evidence/compatibility)).

In the tested migration sample, JSON-serialized HAST matches. Raw JavaScript
objects can differ where Shiki includes a property such as `data: undefined`
that Ferriki omits. Multi-theme token output also differs: Ferriki's `htmlStyle`
is a CSS string and the result includes aligned `variants`; Shiki 4.4.3 uses an
`htmlStyle` object and has no `variants` field. Normalize these shapes in a
custom token renderer, or use `codeToHtml` and `codeToHtmlWithCss` for rendered
HTML.

## Before you switch

1. Confirm that every deployment target can install a Ferriki native binary.
2. Run your build from an installed package in CI, not from a checkout.
3. Keep the Shiki implementation behind the same interface until the switch is
   done, so a target without a binary can fail the deployment explicitly.

The full guide, including asset loading, output-shape differences, and
downstream adapter boundaries, is
[docs/migrations/shiki-to-ferriki.md](https://github.com/sebastian-software/ferriki/blob/main/docs/migrations/shiki-to-ferriki.md).

The repository also contains a separate optional Vite adapter. It transforms
marked HTML and JSX during a build; it does not run in the browser and has not
been published with the current `@ferriki/core` release. See the
[@ferriki/vite source README](https://github.com/sebastian-software/ferriki/tree/main/node/vite)
for its current contract and release status.
