# Benchmarks

A CMS or site build can highlight hundreds of blocks with one loaded
highlighter. That repeated work is the headline here: on our 14-file corpus,
Ferriki was **4.7× faster than Shiki/WASM on Linux x86-64** and **5.5× faster
on macOS ARM64**. Ferriki and both Shiki engines produced identical HTML for
every repository file on both hosts.

These factors are Shiki's time divided by Ferriki's time. They describe this
corpus and these machines; they do not measure total build time or guarantee
the same factor for another workload.

## First use and the regex prefilter

Keep the default prefilter for a CMS, documentation server or site build that
reuses its highlighter. For a short-lived process, `regexPrefilter: false`
avoids building the regex prefilter. Choose it when creating the highlighter;
it is not a per-render option. Rust exposes the same choice through
`.with_regex_prefilter(false)`.

<RegexModeBenchmarks />

In this run, disabling the prefilter shortened the full-corpus first use by
**35–37%**, while repeated repository highlighting took **51–68% longer**.
First use includes package imports, highlighter setup and one render of all
14 files. It excludes process creation and asset downloads, and does not
measure the latency of one isolated snippet. The on/off reports ran in
separate, fixed-order windows, so their raw differences are observations.

The top-level `codeToHtml()` shorthand uses a shared singleton. Calling that
function once per block does not create a fresh highlighter for every block.
See [reuse a highlighter](/guide/getting-started#reuse-a-highlighter) and
[factory options](/guide/api#highlighter-options).

### What changes when the prefilter is disabled?

<JsonAstroModeDifferences />

On Linux, Ferriki's JSON/Astro off timings were roughly 2–3.5% longer. On
macOS, they were roughly 17–22% shorter, but the unchanged Shiki controls also
became roughly 16–23% faster. That shared movement indicates drift between
the measurement windows. It does not establish a prefilter benefit for JSON
or Astro. A causal comparison needs repeated, alternating runs on one host.

## Method

1. **Same output before timing.** Ferriki and both Shiki engines must produce
   identical serialized HTML. Curated and TIOBE reports also check source
   preservation. Errors, timeouts, missing cases and invalid samples fail the
   Blacksmith job, with diagnostics retained.
2. **Warm repository timings.** One loaded highlighter per engine. Five warmup
   rounds precede at least 30 samples and a target budget of 1.5 seconds per
   eligible engine per document. Engine order rotates every round. Totals sum
   per-document medians; they are not a single timed batch.
3. **Warm curated and TIOBE timings.** One fresh worker per language, reused
   highlighters, five warmup calls, at least 30 rounds, a shared target budget
   of 300 ms per engine, and a cap of 1,000 rounds. Every sample is retained.
   Setup diagnostics are excluded and are not fair cold-start comparisons.
4. **Cold repository timings.** Ten fresh processes per Node engine. Timing
   starts before engine-specific imports and includes setup and rendering the
   corpus once. Engines run in Ferriki, Shiki/WASM, Shiki/JS order. Process
   creation is outside the clock; grammar and theme assets are locally cached.
5. **Separate machines, serial work.** Each host builds one release addon,
   then runs repository, curated and TIOBE workloads serially, with prefilter
   on then off per corpus. Builds and other benchmarks do not share a timing
   window. Compiler, addon hash, source revision and fixture hashes are recorded.

The repository corpus contains real files from Ferriki and its unchanged
upstream mirrors. The curated corpus covers 20 formats, including embedded
languages. The TIOBE selection remains pinned to September 2026; Scratch is
explicitly unsupported. Prism uses independent grammars, so its retained
timings do not claim TextMate output parity.

The optional Phiki comparison was skipped on both Blacksmith hosts. This run
has no PHP performance claim. The repository harness can also measure pinned
Phiki 2.2.1 when PHP 8.3+, mbstring/Oniguruma and Composer dependencies are
available; it compares visible text and per-character styles separately from
the strict Node HTML gate.

## Reproduce

Run both paid Blacksmith profiles manually from the repository root:

```sh
gh workflow run blacksmith-comparison.yml --ref main -f platform=both
```

Or measure locally, keeping the machine idle:

```sh
cd node
pnpm install --frozen-lockfile --ignore-scripts
pnpm run build:compat
pnpm run build:native
node scripts/run-blacksmith-comparison.mjs /tmp/ferriki-comparison
```

To reproduce the recorded inputs, check out the measured revision
`ad991d0d1cbcc8e5f24d5cbcc95d3468425323db` first. A current checkout measures
the current sources. Reports describe workspace builds; they do not certify
registry artifacts. The [workflow guide](https://github.com/sebastian-software/ferriki/blob/main/docs/benchmarks/blacksmith.md)
covers artifact retention and interpretation.
