# Benchmarks

A CMS or site build can highlight hundreds of blocks with one loaded
highlighter. In the October 25 capture with Ferroni 2.7.2 on our
14-file corpus, Ferriki was **3.7× faster than Shiki/WASM on Linux x86-64**
and **4.3× faster on macOS ARM64**. Ferriki and Shiki/WASM produced identical HTML for
every repository file on both hosts.

These factors are Shiki's time divided by Ferriki's time. They describe this
corpus and these machines; they do not measure total build time or guarantee
the same factor for another workload.

## Four regex policies

The timing tables use the [Ferroni 2.7.2 shared-storage capture](https://github.com/sebastian-software/ferriki/tree/main/docs/benchmarks/blacksmith/2026-10-25-shared-storage).
The runtime shares program and group sections of each decoded container instead
of copying both buffers. Fresh processes reuse unpacked packages populated before timing. The separate
[local startup diagnostic](https://github.com/sebastian-software/ferriki/tree/main/docs/benchmarks/precompiled-patterns/decoded-cache)
also measures the first cache fill and setup without rendering. The earlier
Blacksmith capture and its memory measurements remain available below.

The October 25 repository build measures **Source Off**, **Source Auto (lazy
DFA)**, **Source Eager**, and **Prepared** as separate contenders. The source
paths do not open prepared archives. Prepared remains the product default;
these explicit configuration and diagnostic APIs are repository additions
after npm 1.2.0.

Tables scroll horizontally on narrow screens. Focus a table and use the arrow
keys to compare every column.

On macOS, Prepared reaches first HTML in **277 ms**, compared with **453 ms**
for Source Eager and **1,225 ms** for Shiki/WASM. On Linux it takes **470 ms**,
slightly longer than Source Eager's **446 ms** and about half Shiki/WASM's
**947 ms**. Source Off still has the cheapest first use on both hosts.
Repeated Prepared rendering is **3.7× faster than Shiki/WASM on Linux** and
**4.3× on macOS**, and close to or faster than Source Eager on this corpus.

## Prepared regex

Ferriki can carry regex preparation across process restarts. With Ferroni 2.7,
standard grammars arrive with precompiled programs and prepared Eager scanner
automata. A fresh highlighter restores that work instead of rebuilding the
serialized automata from source. The digest-addressed disk cache lets later
builds reuse the download when their cache persists.

An October 24, 2026 local diagnostic compares source Eager with full static
preparation on macOS ARM64, using Ferroni 2.7.0 and Rust 1.99.0. Two runs
rotate four lanes through 20 fresh-registry samples after one discarded round.
The table reports startup medians in milliseconds as run A / run B.

| Grammar    |      Source Eager |  Prepared Eager |
| ---------- | ----------------: | --------------: |
| C++        | 143.699 / 144.585 | 67.955 / 68.083 |
| Swift      |   33.564 / 34.004 | 15.511 / 15.648 |
| Rust       |     3.629 / 3.605 |   1.680 / 1.677 |
| Python     |   12.986 / 13.074 |   6.559 / 6.613 |
| JSON       |     0.464 / 0.468 |   0.387 / 0.383 |
| CSS        |   36.163 / 36.587 | 12.889 / 12.987 |
| TypeScript |   72.606 / 72.024 | 23.682 / 23.360 |

For C++, that is **about 53% lower tokenizer startup**, from roughly 144 ms to
68 ms. Prepared execution stays comparable to ordinary Eager across these
workloads. All lanes must produce identical token arrays; prepared lanes also
verify that real groups load without falling back to source scanner assembly.

Startup includes compressed SHA-256 verification, copying, bounded
decompression, archive opening, theme and grammar construction, and the first
document. Network, file I/O, grammar JSON parsing, HTML rendering, and complete
builds are outside the timer. This measures tokenizer restoration versus
preparation, not end-to-end CDN startup or deployment speed. Restoration still
costs more than source Off. CPU placement and thermals were uncontrolled.

The [full diagnostic and both raw captures](https://github.com/sebastian-software/ferriki/blob/main/docs/benchmarks/precompiled-patterns/prepared-eager.md)
record execution timings, fixture hashes, package sizes, source provenance,
and limits. This diagnostic measures isolated primary grammars; production
packages also carry dependency and injection scanner groups. The Blacksmith
comparisons below measure the full Node HTML path with prepared standard
packages, independently of this source-Eager diagnostic.

## Process memory

A separate Blacksmith run measures the complete Node process, including Rust
and WASM memory. It uses the same two runner profiles as the timing suite,
with one dedicated VM per profile. Six fresh processes per engine and workload
run serially in rotating order; every process result is retained.

The shared repository cohort contains **12 files** and runs 50 passes with one
loaded highlighter: **600 rendered documents**. YAML is excluded for all engines
because Shiki/JS cannot translate the grammar. SQL is also excluded because
Shiki/JS differs from native/WASM on that fixture in a fresh isolated process.
This memory cohort is separate from the 14-file timing corpus above. The second
workload repeats the TypeScript API source with newline separators to at least
256 KiB and renders it ten times. All three engines pass exact HTML SHA-256
and byte-length agreement for both measured workloads before measurement.
Each HTML result is consumed and released before the next document.

In this capture, Ferriki's median RSS after the 12-language repository workload
was **51–137% higher than Shiki/WASM**: 689.0 versus 454.8 MiB on Linux and
1,071.3 versus 451.9 MiB on macOS. For the generated large TypeScript case,
with only TypeScript requested, it was **33–55% lower**. These workloads do not
load the entire grammar catalog. Ferriki loads the requested languages and
needed dependencies; a package can include embedded and injected grammars.

The previous capture's 27–31% repository memory saving does not hold in this
capture. Both hosts used Ferriki 1.2.0, Shiki 4.5.0, Ferroni 2.7.0, Node 24.21.0
and Rust 1.99.1 at revision `2b16844`. The tables retain every engine,
initialization and peak values, and min–max ranges. These observations describe
the recorded workloads; a controlled A/B run is needed to attribute changes to
one runtime feature.

### Peak process memory

<MemoryBenchmarks metric="peakRss" />

RSS measures resident memory for the whole process. The peak is the OS
high-water mark from startup through the final render checkpoint, including
imports, inputs, initialization, rendering and explicit V8 garbage collection.
It is not a render-only allocation peak. Initialization and render checkpoints
use two explicit V8 collections separated by event-loop turns; no collection is
forced between documents. Raw pre-GC values and checkpoints after 1, 10 and 50
repository passes (1, 5 and 10 large-document renders) remain in the archive.

V8 heap measurements alone would miss Rust allocations. The raw reports retain
heap, external and ArrayBuffer fields as diagnostics, without adding them to
RSS. Native allocators and WASM can retain pages after V8 GC, so retained RSS
does not by itself establish a leak. These are bounded sequential workloads;
they do not measure allocation counts, concurrent capacity or a production
memory limit. Compare engines within each host; the two operating systems
account for memory differently.

The [memory capture](https://github.com/sebastian-software/ferriki/actions/runs/40135588303)
and [committed memory archive](https://github.com/sebastian-software/ferriki/tree/main/docs/benchmarks/blacksmith/2026-10-24-prepared-eager/memory)
retain the source revision, engine versions, hardware, build receipts, every
worker result and original checksums. The homepage build validates this archive
before generating its tables. See the
[memory method and reproduction steps](https://github.com/sebastian-software/ferriki/blob/main/docs/benchmarks/blacksmith.md#process-memory).

## First use and the regex prefilter

<BlacksmithSummary firstUse />

The default lane restores prepared regex packages. `regexPrefilter: false`
disables the prefilter and skips those packages. Choose it when creating the
highlighter; it is not a per-render option. Rust exposes the same choice through
`.with_regex_prefilter(false)`.

<RegexModeBenchmarks />

In this run, disabling the prefilter made repeated repository highlighting
**2.8% shorter on Linux** and **1.4% longer on macOS**. Full-corpus first use
was **66–74% shorter** with it disabled. First use includes package imports,
highlighter setup and one render of all 14 files. All 14 languages are loaded
up front; this is not the startup latency of one isolated snippet. Process
creation and asset downloads are excluded. The on/off reports ran in separate,
fixed-order windows, so their differences are observations, not isolated
configuration effects. Prepared optimization still has substantial restoration
cost in this many-language workload.

The top-level `codeToHtml()` shorthand uses a shared singleton. Calling that
function once per block does not create a fresh highlighter for every block.
See [reuse a highlighter](/guide/getting-started#reuse-a-highlighter) and
[factory options](/guide/api#highlighter-options).

## Method

1. **Same output before timing.** Ferriki and both Shiki engines must produce
   identical serialized HTML for supported cases. Shiki/JS cannot translate
   the current YAML grammar, so YAML and its full-corpus warm and cold totals
   are explicitly unsupported. Its other 13 repository files pass exact HTML
   agreement. Curated and TIOBE reports also check source
   preservation. Errors, timeouts, missing cases and invalid samples fail the
   Blacksmith job, with diagnostics retained.
2. **Warm repository timings.** One loaded highlighter per engine. Five warmup
   rounds precede at least 30 samples and a target budget of 1.5 seconds per
   eligible engine per document. Engine order rotates every round. Totals sum
   per-document medians; they are not a single timed batch.
3. **Warm curated and TIOBE timings.** One fresh worker per language, reused
   highlighters, five warmup calls, at least 30 rounds, a shared target budget
   of 300 ms per engine, and a cap of 1,000 rounds. Every sample is retained.
   Setup diagnostics are excluded and are not fair cold-start comparisons.
4. **Cold repository timings.** Ten fresh processes per Node engine. Timing
   starts before engine-specific imports and includes setup and rendering the
   corpus once. Eligible engine order rotates each round. Process creation is
   outside the clock; grammar and theme assets are locally cached.
5. **Independent corpus VMs.** Each profile uses one VM per corpus. All engines
   and both prefilter modes for that corpus run serially on the same VM, with
   prefilter on then off. Independent corpora run concurrently on separate VMs.
   A merge validates every report, checksum, build input and CPU model before
   joining the evidence. The Linux merge failed the CPU check in this capture;
   successful corpus shards are published separately with their own context. Repository totals and JSON/Astro are separate corpus observations;
   timings from different VMs are never combined into one comparison. Each VM's
   compiler, addon hash, source revision and fixture hashes are retained.

The repository corpus contains real files from Ferriki and its unchanged
upstream mirrors. The curated corpus covers 20 formats, including embedded
languages. The TIOBE selection remains pinned to September 2026; Scratch is
explicitly unsupported. Prism uses independent grammars, so its retained
timings do not claim TextMate output parity.

The optional Phiki comparison was skipped on both Blacksmith hosts. This run
has no PHP performance claim. The repository harness can also measure pinned
Phiki 2.2.1 when PHP 8.3+, mbstring/Oniguruma and Composer dependencies are
available; it compares visible text and per-character styles separately from
the strict Node HTML gate.

## Reproduce

Run both paid Blacksmith profiles manually from the repository root:

```sh
gh workflow run blacksmith-comparison.yml --ref main -f platform=both
```

To run the separate memory suite:

```sh
gh workflow run blacksmith-comparison.yml --ref main -f platform=both -f suite=memory
```

Or measure locally, keeping the machine idle:

```sh
cd node
pnpm install --frozen-lockfile --ignore-scripts
node scripts/check-benchmark-versions.mjs
node ../scripts/materialize-assets.mjs --sources
pnpm run build:native
node scripts/run-blacksmith-comparison.mjs /tmp/ferriki-comparison
node scripts/run-blacksmith-memory.mjs /tmp/ferriki-memory
```

To reproduce the recorded inputs, check out the measured revision
`2b16844ed26da3d58a8198e362cd467f777bea7d` first. A current checkout measures
the current sources. Omit the registry freshness check when reproducing a dated
archive with its recorded comparator pins. Reports describe workspace builds; they do not certify
registry artifacts. The [workflow guide](https://github.com/sebastian-software/ferriki/blob/main/docs/benchmarks/blacksmith.md)
covers artifact retention and interpretation.

## Rust syntect comparison

This separate Rust experiment compares syntect 5.3.0 with `regex-onig` and
`regex-fancy` against Ferriki 0.13.0. It measures complete HTML-highlighting
calls on the same pinned source documents. Each engine uses its own grammar
catalog and dark theme: syntect uses `base16-ocean.dark`, while Ferriki uses
`nord`. Grammars, scopes, theme colors, and markup differ, so these observations
do not establish output parity or a speedup for equivalent work.
The Ferriki measurements use the shared 0.13.0 base runtime before the
scanner-cache work tracked in issue #230, so they do not include that change.

The pinned set contains 20 formats. Syntect's default syntax set resolved exact
grammars for 11; Astro, Svelte, Swift, TSX, Vue, MDX, SCSS, TOML, and TypeScript
were excluded without fallback substitutions. The [comparison guide](/guide/ferriki-and-syntect)
covers the catalog and migration boundaries; the [capture archive and method](https://github.com/sebastian-software/ferriki/tree/main/docs/benchmarks/syntect/2026-10-10)
contains the resolved names, all 20 fixture hashes, six raw reports, support
probes, binary receipts, and checksums.
