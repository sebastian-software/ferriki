# Historical precompiled pattern diagnostics

These measurements used the earlier gzip/postcard transport. The program-only
policy inferred below was superseded by the [prepared Eager integration](prepared-eager.md).
Warm Auto was not the intended execution baseline. Reproduction now uses the
new container and therefore cannot reproduce the historical byte counts.

Local characterization for [#325](https://github.com/sebastian-software/ferriki/issues/325),
using Ferroni 2.6.0 on macOS arm64, rustc 1.99.0, the workspace release profile
(fat LTO, one codegen unit) and the locked curated grammar sources.

The question is whether gzip decompression, archive indexing and lazy program
loading cost less than source compilation in a fresh registry. Both lanes use
the same engine, grammar and source fixture. Archive generation and JSON parsing
are outside the timer. Archive copying, decompression, indexing, registry
construction, tokenization and teardown are inside it. Each sample uses a new
registry; one warmup pair precedes 20 measured pairs in alternating order.
Token arrays must agree before timing begins.

## Observations

Times are milliseconds, median with observed minimum–maximum. These are local
diagnostics, not a cross-platform or end-to-end cold-process performance claim.

| Grammar / prefilter | Source compilation     | Compressed archive     |
| ------------------- | ---------------------- | ---------------------- |
| C++ / off           | 42.807 (42.170–43.513) | 31.147 (29.740–32.291) |
| C++ / on            | 61.652 (59.710–63.408) | 42.086 (40.380–43.445) |
| Swift / off         | 7.199 (6.672–7.594)    | 6.579 (5.867–7.011)    |
| Swift / on          | 11.306 (10.520–11.980) | 9.341 (8.681–10.084)   |
| JSON / off          | 0.230 (0.218–0.396)    | 0.245 (0.232–0.322)    |
| JSON / on           | 0.283 (0.271–0.443)    | 0.278 (0.265–0.428)    |

C++ shows a material reduction even after decompression. Swift benefits less;
JSON is within the observed noise and slightly slower with the prefilter off.
The C++ archive shrinks from 7,064,749 uncompressed bytes to 557,884 bytes with
gzip. Swift's compressed archive is 168,853 bytes; JSON's is 2,615 bytes.
The 94 standard sidecars total 6,921,843 bytes in addition to 3,884,304 bytes of
grammar payloads. These bytes remain CDN data, outside the published packages.

## Historical reproduction and limits

```sh
cargo run --release -p ferriki-textmate --example precompiled_startup -- \
  assets/upstream/curated/grammars/cpp.json \
  node/benchmarks/curated/fixtures/orders.cpp
```

Use `swift.json` with `Orders.swift` or `json.json` with `orders.json` for the
other rows. The example loads one grammar, without external grammar dependencies,
network transfers, theme application or HTML rendering. It isolates program
loading costs; it does not measure complete application startup or the extra
network transfer on an empty cache.

The separate `cargo test --test precompiled_assets` differential gate exercises
the complete standard catalog's dependency loading and themed output on all 20
curated fixtures and the 12 standard TIOBE fixtures, with both prefilter settings.
Seven TIOBE grammars are custom imports without standard sidecars; Scratch has
no TextMate grammar. Missing, corrupt, malformed and incompatible sidecars have
explicit fallback coverage. The unchanged native compatibility gate covers the
Node surface and custom-grammar behavior.

## Ferroni 2.7 follow-up

Ferroni 2.7 stabilizes `PrecompiledEager`, a bound pair of ordinary programs and
portable prepared scanner groups. HTTP and compression remain the host's
responsibility. The sidecar container now supports this stable pair, with scope
binding for registries that load multiple languages.

The same C++ fixture, toolchain, platform and release profile were measured
again, using 20 alternating fresh-registry samples after one warmup pair.
The source-only lane retains automatic acceleration. The program-only archive
also retains automatic acceleration; the sampled Eager archive enables Eager
only when prefiltering is on. Both include full archive copying, decompression,
indexing, lazy loading, tokenization and teardown in the timed boundary.

| Archive policy / prefilter | Source only, ms median (range) | Archive, ms median (range) | Compressed bytes |
| -------------------------- | ------------------------------ | -------------------------- | ---------------- |
| Programs / off             | 40.148 (38.941–41.728)         | 33.882 (32.962–35.704)     | 557,876          |
| Programs / on              | 58.871 (57.404–60.123)         | 44.808 (43.672–46.450)     | 557,876          |
| Sampled Eager / off        | 39.884 (38.818–42.264)         | 63.107 (61.297–65.368)     | 3,142,507        |
| Sampled Eager / on         | 58.823 (57.206–61.609)         | 77.193 (75.791–78.862)     | 3,142,507        |

The Eager archive was trained on the measured snippet itself, so this is a
favorable coverage case, not a held-out generalization result. It still regressed
startup because the larger archive costs more to load. An earlier diagnostic
that enumerated every static scanner list was larger still: about 12.7 MB
compressed and 187 ms with prefiltering on. That enumeration path was removed.
These measurements say nothing about long-running Eager throughput or other
deployment/transport choices.

The earlier standard generator therefore shipped program-only archives. The 94 files then
totaled 6,924,670 compressed bytes, including the versioned container. Rust hosts
can opt into `SyncRegistry::precompile_patterns(scope, samples)` and measure
their own workload. The historical example accepted `--eager`; the current example uses `--sampled`
for its updated sample-driven comparison. The correctness tests assert actual group loads,
zero invalid-group fallbacks, preserved tokens/warnings, external includes and
injections, and separate sources for multiple root grammars.

## Warm execution follow-up

The startup results above cannot establish repeated execution speed. A second
diagnostic separates archive loading and first tokenization from reused-grammar
execution, comparing four lanes on Ferroni 2.7: source/Auto, bytecode/Auto,
source/Eager and prepared/Eager. Each lane retains its grammar and scanners,
resets the document stack per call and allocates the same binary token output.
All outputs agree before timing. Sixty-four warmup documents precede at least 30
rotating measurement rounds per case, with a 1.2-second case budget. Fixture
length and a 16-copy input are both measured. Prefilter coverage and built/retired state must stay unchanged during each
measurement. The complete run was repeated.

The table reports median milliseconds for the 16-copy input. These are
tokenizer results on the same local macOS arm64/release toolchain, excluding
archive copying, decompression, compilation, warmup and teardown. The input is
one grammar at a time, without external grammar dependencies, theme application
or HTML rendering. It does not establish the speed of upgrading from an older
Ferroni: every lane here uses 2.7.

| Grammar    | Bytecode/Auto A / B | Prepared/Eager A / B |
| ---------- | ------------------- | -------------------- |
| C++        | 5.6355 / 5.5836     | 5.7076 / 5.6025      |
| Swift      | 2.7597 / 2.7363     | 2.6741 / 2.6439      |
| Rust       | 2.0515 / 2.0354     | 2.0588 / 2.0363      |
| Python     | 3.3429 / 3.3333     | 3.3064 / 3.2965      |
| JSON       | 1.7933 / 1.8537     | 2.0558 / 2.1279      |
| CSS        | 3.4523 / 3.4043     | 3.3836 / 3.3555      |
| TypeScript | 4.4648 / 4.4622     | 4.4230 / 4.4256      |

Prepared groups actually load: C++ reports 43 loaded records, zero invalid
records and 91 built scanner prefilters after warming, versus 56 built under
Auto. No scanner prefilters were retired in either lane. Swift loads 41 groups;
the other five languages load 5–42 each. Thus an inactive archive or wholesale
prefilter retirement does not explain the lack of a large warm improvement.

The result is workload-dependent: C++/Rust/TypeScript are close, Swift improves
by about 3%, and JSON takes about 15% longer. Source/Eager and prepared/Eager
are also close. Ferroni's `ScannerConfig::acceleration` documents the relevant
policy: Auto prepares suitable search accelerators after warmup, while Eager
prepares them before construction returns and includes tiny sets that Auto
skips. Loading prepared groups removes repeated preparation work; the API does
not promise a universally faster execution path than an already warm Auto
scanner. JSON shows why accelerating additional tiny sets can cost throughput.

The earlier program-only policy was inferred from these comparisons. That
inference did not answer the intended source-Off loading / Eager execution
objective and has been superseded. The [current diagnostic](prepared-eager.md)
uses the corrected baseline and transport.
