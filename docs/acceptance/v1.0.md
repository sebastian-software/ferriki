# Ferriki 1.0 release acceptance

This record documents the release-readiness work in #249 and the
pre-publication decision for #248. Final 1.0 publication remains an explicit
follow-up gate in those issues. The original audit is retained in those
issues; this record uses the integrated candidate after the corrections.

## Candidate and publication policy

The stabilization candidate is **0.14.0**, a stable pre-1.0 version published
through the normal workflow with npm **`latest`**. It is not a SemVer
prerelease. A `next` dist-tag does not make a stable Rust or npm version a
prerelease. The candidate consumes no 1.0 version number.

Candidate source: [`1e8d363ee01c8c60af42d78e8129b74ed22fd362`](https://github.com/sebastian-software/ferriki/commit/1e8d363ee01c8c60af42d78e8129b74ed22fd362),
tag [`v0.14.0`](https://github.com/sebastian-software/ferriki/releases/tag/v0.14.0).
The synchronized 18-file release diff was independently reviewed in #238.
The registry publication result is recorded below.

All six audit findings are resolved: #242 through #250/#253, #243/#244 through
#253, #245 through #255, and #246/#247 through #256. The callback contract in
#241 is protected by #252 after native decorations landed in #250. Each
implementation PR was reviewed and merged only with green checks on its
reviewed head. The publication gate additionally requires normal main CI on
the exact release commit, rather than accepting a different PR head.

## Accepted surface and migration

The reviewed contracts are ADRs 0011, 0014, 0017 and 0018 and the linked
[Node contract](../ferriki-1.0-api-contract.md), [Node API](../ferriki-api.md),
[Rust API](../rust-api.md), [macro guide](../inline-code-macros.md), and
[Shiki migration guide](../migrations/shiki-to-ferriki.md).

- Node is ESM-only and requires Node >=22.13.0. The seven supported targets
  are Linux x64/arm64 with glibc or musl, macOS arm64, and Windows x64/arm64
  with MSVC. There is no browser/WASM highlighting runtime or macOS Intel
  sidecar.
- Public Node results are HTML and HTML/CSS. The macro subpaths prepare
  output at build time through the optional matching-version `@ferriki/vite`
  package. Transformer token/HAST callback data does not restore standalone
  structured-output methods. Such callers must migrate to HTML or Rust's
  token APIs.
- The primitive/singleton aliases documented as shims remain migration
  compatibility. Engine injection, ANSI parsing and `colorReplacements`
  remain non-goals. Callback context fields follow their documented stage;
  consumers must guard `pre` and `code` when a hook can run before allocation.
- Standard assets are release-pinned, asynchronously downloaded and digest
  verified. Offline deployments must populate the cache or supply explicit
  registrations. Failed singleton initialization can be explicitly retried;
  it does not add an automatic network retry policy.
- The three public Rust crates retain their documented tokens, HTML,
  UTF-8 offsets, feature boundaries and curated semver surfaces.
  `ferriki-core` remains private, as do explicitly excluded native bridges.
- #122, #240 and #241 are complete. #152 grammar curation and #221 direct
  React JSX output remain independent follow-ups. No new API is required
  to call this release complete. #254 tracks Rust semver checking against
  the first real 1.x release baseline.

## Decision and recovery

**[2026-10-10 decision](https://github.com/sebastian-software/ferriki/issues/248#issuecomment-6102196764): GO for deliberate 1.0 versioning.** I accept the
0.14.0 stabilization candidate on the evidence above and am proceeding with
`Release-As: 1.0.0`. The six audited defects, callback-contract protection,
public package/source/provenance checks, all supported targets and current
consumer fixtures are complete. The reviewed product scope and bounded
sidecar growth are acceptable; #152, #221 and #254 remain explicit follow-ups.

This decision authorizes preparation of the generated 1.0 release PR. Its
synchronized versions and lockfiles still require review and green exact-head
checks before merge. The release's own main CI, both registry verifiers and
fresh final-version consumers remain required before closing #248/#249.

The [release checklist](../release-checklist.md) is the procedure for both
registries, all sidecars and the Vite integration. If publication is partial,
stop promotion and resume the original immutable release tag:

```sh
gh workflow run publish.yml --repo sebastian-software/ferriki --ref v0.14.0 \
  -f force-publish=true -f release-tag=v0.14.0 -f dist-tag=latest
```

For 1.0 recovery, replace both tag arguments with `v1.0.0`. Existing npm
versions must pass identity/provenance consistency checks and are skipped when
the chosen dist-tag is already correct. Missing versions are published.
Both public registry verifiers must pass before the summary says `PUBLISHED`.
Never republish a version or run recovery for an older tag from newer main.
Moving a dist-tag requires the separately documented npm Trusted Publisher
permission; that settings permission was not independently inspected.

If a published version is defective, deprecate affected npm packages with a
specific migration message and release a corrected version. For example,
after the replacement actually exists:

```sh
npm deprecate '@ferriki/core@<bad-version>' 'Upgrade to <fixed-version>: <specific reason>'
```

Apply the same decision to affected sidecars/Vite. For an unusable Rust
release, assess `cargo yank --version <bad-version> <crate>` for each affected
crate and publish the correction. These are recovery instructions, not actions
performed as part of this acceptance.

## Final 1.0 publication

The deliberate 1.0 release follows this record. #248 and #249 must remain open
until the generated 1.0 version diff is reviewed, exact-source CI and release
verification pass, and the final public consumer/provenance evidence is
attached there. The 0.14.0 evidence above must not be relabeled as 1.0 proof.
