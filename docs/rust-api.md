# Ferriki from Rust

The `ferriki` crate is the synchronous, reusable highlighter. It contains no
Node.js or N-API dependency. `ferriki-core` is the private N-API host and uses
the same grammar, theme, tokenizer, and renderer implementation.

## Assets and lifecycle

Ferriki does not embed all standard grammars into the library. An application
supplies the generated `assets/shiki` directory from this repository (or the
same files packaged with that application):

```text
assets/shiki/
  languages/manifest.fkindex
  languages/*.fkgram
  themes/manifest.fkindex
  themes/*.fktheme
```

No `node/ferriki` directory is required. `StandardAssetCatalogs::load_from_root`
reads the two manifests at construction time. Grammar and theme payloads are
decoded only on first use, then cached by the catalogs and the highlighter.
`StandardAssetCatalogs::from_embedded` accepts the same two manifests and maps
from asset filenames to `Cow<'static, [u8]>` for applications using
`Cow::Borrowed(include_bytes!(...))`. Borrowed payloads are not copied at
construction. The
manifests contain aliases, embedded-language references, and injection metadata
in both modes. Missing payloads and incompatible format versions are typed
errors. The binary format is versioned but remains an internal format; keep
assets and the Rust crate from the same Ferriki release.

```toml
[dependencies]
# Use the version of the matching Ferriki release; crates and npm share it.
ferriki = "<version>"
```

Before the first crates.io release, use a Git or local path dependency for this
repository and its matching assets. The checked-in, compiled
[`rust_consumer` example](../examples/rust_consumer.rs) runs with
`cargo run -p ferriki --example rust_consumer -- assets/shiki`. The public
[`Highlighter` API](../src/highlighter.rs) also carries a
compiling Rustdoc example.

```rust
use std::path::Path;
use ferriki::{Highlighter, RenderOptions, StandardAssetCatalogs, render_html_lines};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let assets = StandardAssetCatalogs::load_from_root(Path::new("assets/shiki"))?;
    let mut highlighter = Highlighter::builder()
        .with_assets(assets)
        .load_languages(["rust", "typescript"])
        .load_themes(["nord"])
        .build()?;
    let tokens = highlighter.highlight("fn main() {}", "rust", "nord")?;
    let line_html = render_html_lines(&tokens, &RenderOptions::default());
    assert_eq!(line_html.len(), 1);
    Ok(())
}
```

Builder loads are eager. Unlisted standard grammars and themes remain lazy and
can be loaded on the same highlighter later. A highlighter is intended for reuse
across blocks and documents. Its `&mut self` methods make registry and cache
mutation explicit. `StandardAssetCatalogs` can be moved to a worker thread,
but a built `Highlighter` is `!Send` because the TextMate registry uses `Rc`
state. Build one highlighter within each worker thread. A highlighter may
also be built without standard assets when only custom registrations are used.
Dropping it releases its registry and caches.

`highlight` returns typed themed tokens, one vector per source line, including
a final empty line after a trailing newline. Token offsets in this public Rust
API are UTF-8 byte positions in the full input. The existing Node facade keeps
UTF-16 offsets for JavaScript compatibility. `render_html` creates Ferriki's
standalone `<pre><code>` output. `render_html_lines` creates escaped, balanced
inner HTML per line, without code-block or line wrappers.
`Highlighter::highlight_html_lines` returns a `HighlightedLines` value with
line HTML, foreground, background, and theme name. It takes the direct route
when only HTML is needed and skips token offset conversion. The output is trusted
only as generated by Ferriki; do not concatenate unescaped metadata into it.

For custom grammars, use `LanguageRegistration::new(id, grammar)` with a parsed `RawGrammar`, or
`register_language_json`. For custom themes, use `ThemeData` (produced by
`parse_theme_data` or `ThemeData::new`), or `register_theme_json`.
`Error::kind()` distinguishes asset I/O, incompatible assets, invalid custom
registrations, unknown languages/themes, tokenization, theme, and internal
failures. `TokenizeOptions` exposes the same resource limits as the Node core.
An overlong line is returned as a plain token, matching the Node behavior;
tokenizer failures use `ErrorKind::Tokenization`.

Options and output records are non-exhaustive so later releases can add fields.
Construct `TokenizeOptions` and `RenderOptions` with `Default` and their
`with_*` methods; inspect output records without exhaustive destructuring.
Tokenization defaults to a 500 ms per-line limit, unlimited line length (`0`),
and no token type or scope metadata. Rendering merges whitespace by default,
does not merge other adjacent styles, emits theme colors, and sets `tabindex="0"`.
Tokens serialize with camelCase fields, `type` for the optional token type, and
`fg`/`bg` on the enclosing result. Absent optional fields are omitted. Rust
offsets remain UTF-8 bytes even when serialized; only the N-API host converts
its results to the JavaScript UTF-16 contract.

`Error` owns a category, message, and optional source error. It deliberately
does not promise `Clone` or `Eq`; compare `kind()` for fallback decisions and
use `std::error::Error::source()` for diagnostics. Tokenizer regex errors and
asset codec errors have crate-owned types, so their public signatures do not
commit consumers to ferroni's or bincode's error representations.
`ferriki::__private` is a semver-exempt bridge for the N-API host, including its
UTF-16 highlighter and multi-theme records. Applications use `Highlighter`.

## Verified asset sources

`StandardAssetCatalogs::from_source` accepts the two binary manifests, trusted
release metadata, and an `AssetSource`. Metadata maps `languages/<asset_file>`
and `themes/<asset_file>` to `AssetMetadata::new(digest, byte_size, format_version)`.
Parse release digests with `str::parse::<AssetDigest>()`. Computing a digest
from downloaded bytes is not a substitute for a trusted release digest.

`DirectoryAssetSource` reads files named by their SHA-256 digest;
`EmbeddedAssetSource` borrows or owns a map from digests to payload bytes.
Custom sources implement `AssetSource::read`. Sources must be `Send + Sync`;
catalog construction validates metadata without reading any payload. On first
load, the catalog checks size and SHA-256 before decoding, then validates the
decoded format version. Only valid, decoded payloads enter the catalog cache.
Repeated highlighting with explicitly loaded languages and themes does not
read the source again.

`AssetIntegrity` identifies a digest or size mismatch, `AssetFormat` identifies
invalid metadata or an incompatible binary format, and `AssetUnavailable`
identifies a missing offline payload. Other filesystem failures use `AssetIo`.
The original directory and filename-based embedded constructors remain
available for trusted application-owned assets; they validate binary formats
but do not have release digests to verify.

This is the Rust integrity foundation for ADR 0013. Release-manifest generation,
the remote source, Node's asynchronous downloads and cache resolution, and the
optional offline release packages remain tracked by #141. Node packages still
bundle their payloads in this stage. A `FORMAT_VERSION` change requires matching
assets; it is not a promise of backward-compatible binary decoding.

## Ferromark adapter contract

Ferriki owns grammar resolution, tokenization, theme application, and escaping
of highlighted code. Ferromark owns Markdown parsing, the `<pre><code>` and
line wrappers, fence metadata, titles, line numbers, annotations, and fallback.
Ferromark's opt-in `HtmlRenderHooks::highlight_code_block` in
[`ferromark#458`](https://github.com/sebastian-software/ferromark/pull/458)
passes the displayed code, normalized optional language, original info field,
and raw fence metadata separately. The adapter should pass only `code` and
`language` to Ferriki. It must leave metadata in Ferromark's escaped wrapper.

```rust
use ferriki::{Highlighter, RenderOptions};
use ferromark::{CodeHighlightInput, HighlightedCodeBlock, HtmlRenderHooks};

struct FerrikiHook<'a> {
    highlighter: &'a mut Highlighter,
    theme: &'a str,
}

impl HtmlRenderHooks for FerrikiHook<'_> {
    fn highlight_code_block(
        &mut self,
        input: CodeHighlightInput<'_>,
    ) -> Option<HighlightedCodeBlock> {
        let language = input.language?.to_ascii_lowercase();
        let highlighted = self.highlighter
            .highlight_html_lines(input.code, &language, self.theme, &RenderOptions::default())
            .ok()?;
        Some(HighlightedCodeBlock::new(highlighted.lines)
            .with_colors(highlighted.foreground, highlighted.background))
    }
}
```

The adapter lowercases language IDs so common fence spellings such as `Rust`
resolve to the bundled grammar. Returning `None` makes Ferromark render escaped plain code. This policy treats
indented and language-less fenced blocks the same way, and safely handles
unknown languages or asset failures. An application can record non-language
errors before returning `None`. `render_html_lines` matches Ferromark's
normalized line count. Ferromark checks that count again before inserting the
fragments. The default Ferromark renderer has no Ferriki dependency or hook
dispatch cost; consumers opt into the hook path.

Ferromark escapes the theme colors in its `<pre>` style attribute. The
foreground and background belong to the block wrapper; Ferriki's per-token
HTML contains only token-level styles.

The contract is exercised in the Ferriki Rust tests for token offsets, escaped
line fragments, trailing lines, and typed fallback errors. Ferromark's hook
tests cover both fenced and indented blocks and wrapper metadata. A dedicated
`ferromark-ferriki` adapter can use this public API after the crate release;
Ferriki itself does not depend on Ferromark.

## Publishing

The publishable crates are `ferriki-textmate`, `ferriki-asset-gen`, and
`ferriki` (the repository's root package). They share one version with the
`@ferriki/core` npm package and are released by the same Release Please pull request:
merging it tags `v<version>`, and `publish.yml` publishes npm and the three
crates from that release, in dependency order, through crates.io Trusted
Publishing. The `ferriki-core` N-API host remains unpublished. The binary
asset format version links the runtime to its asset bundle. See
[ADR 0012](../adr/0012-publishable-rust-highlighter.md) and the
[release checklist](release-checklist.md).
